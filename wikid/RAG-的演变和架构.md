# RAG 的演变和架构
---
内部技术分享，主要想对齐一下概念：向量 RAG、混合检索、GraphRAG、Agentic RAG 这些词到底指什么；以及一套 RAG 系统大概分哪几层、每层干什么、不同场景怎么选。  
# 1. 背景
大模型自己「记住」的那点知识，拿来做企业问答，经常不太够用：  
- 知道的不全。训练有截止日期，新东西跟不上；公司里的制度、工单、产品细节，通用模型本来就没有。
- 想靠再训练补上，又贵又慢，答完了还不好说依据从哪来。
- 就算接了文档库，口语问题还行，一问编号、错误码、SKU 就容易偏；要串关联、多跳的问题，也常拼不起来。
所以才有 RAG（Retrieval-Augmented Generation，检索增强生成）：把知识放到外面能搜的库里，先搜到材料，再让模型据此组织答案。后面要讲的混合检索、图谱、Agent，主要就是在把最后这一点补好。  
# 2. RAG 的演进
业界对 RAG 能力增强有几种常见方案，针对不同问题场景可以叠加使用，不必按代际替代。它们不是严格的第几代淘汰上一代，而是针对不同类型问题的补强——简单问题用混合检索就够，复杂问题再叠加图谱或 Agent。选型时看问题类型，不看哪个更先进。  
**各方案大致在说什么：**  
**初代 · 全量上下文。**把相关文档整段塞进提示词，靠模型直接答。文档一长就超上下文、又贵又不稳，只适合极短材料。  
**二代 · 基础向量 RAG。**文档切片 → Embedding → 向量库；提问时按语义相似度召回片段，再生成。解决了「找语义相近内容」，但对制度编号、错误码、SKU 这类精确词容易搜不准。  
**三代 · 混合检索 RAG。**在向量检索之外加上关键词检索（常见是 BM25），再做重排序（Rerank）。语义模糊靠向量，专名/编号靠关键词，两路结果融合后精排。多数业务问答的实用基线。  
**四代 · GraphRAG。**在文本检索之外引入知识图谱：先抽实体和关系（系统、故障码、流程节点等），再按图上的边做关联、多跳查询。适合「A 影响哪些下游」「从现象追到根因」这类要串关系的问题；图谱质量差时收益很小。  
**五代 · Agentic RAG。**检索不再是固定「搜一次就生成」，而是由 Agent（或状态机）按问题动态决定：改写问题、选哪路检索、够不够再补搜、最后校验有没有引用。适合多意图、跨库、需要多步查找的问题；简单事实题走这套会又慢又贵。

一般的构建顺序是：先用混合检索做出一个能上线、能打分的基础版本，覆盖大部分日常问答。等实际用起来，发现有些答不好的问题是卡在「要串多个实体的关联、要多步推理、一句话里问了好几件事」这类场景上，再针对性地加图谱和 Agent。不用一开始就让每个问题都走 Agent——简单问题走 Agent 只会更慢更贵。

**注：**Agentic RAG 中的Agent指的是一套检索编排流程（改写 → 选路 → 补搜 → 校验），而不是通用 AI Agent 框架。  
# 3. RAG 系统架构
一个 RAG 系统通常拆成几层，各层干什么、边界在哪。下面 3.1～3.5 按架构主流程展开：数据源 → 加工 → 存储 → 检索 → 接入。图如下：  

## 3.1 数据源层
先保证接得进来：PDF / Word / Markdown、FAQ、工单、表结构、图片截图、图文混合手册等，原始文件丢对象存储（MinIO / S3），加工前后留溯源 ID。权限在检索时就要按文档过滤，别等问题答对了却泄密。  
## 3.2 加工层

## 3.4 检索层
检索层负责拿到问题后，决定去哪儿搜、怎么搜、搜到的东西够不够用。这里要分两种情况，不是所有问题都走同一条路：  
**简单问题走短链路：**看意图 → 选检索路 → 重排 → 生成（带引用）。搜一次就够，不折腾。多数日常问答都是这种，对应混合检索。  
**复杂问题才走完整链路：**看意图 → 改写问题 → 选检索路 → 重排 → 判断信息够不够 → 不够再补搜 → 生成 → 检查有没有引用。比短链路多了「改写」「判断够不够、不够再补搜」这种带回头的循环，这其实就是 Agentic RAG 的流程，只在需要多步查找时才启用。  
不管走哪条，中间这些步骤最好都能被记录和观察到，别做成一个「问题进去、答案出来」、中间看不见的黑盒，不然出了问题很难定位是哪一步的锅。  
**实践建议：**简单事实题走混合检索短链路；只有召回明显不够、多意图或跨库时，才启用完整链路（Agent）。触发条件和轮次预算见第 6 章，这里不重复展开。

向量、关键词等多路检索会各出一份结果，需要合并成一份再往下走。常见两种做法：**RRF**（Reciprocal Rank Fusion，倒数排名融合）——不看原始分数，只看每条结果在各列表里排第几，排名越靠前得分越高，最后合成总排名；**加权合并**——给每路结果乘一个权重再相加，比如向量 0.6 + 关键词 0.4，按总分排序。合并后再用 Rerank（重排序模型）精排出 Top-N。Agent 最多 2～3 轮补搜，超时或超 Token 就降级：给带引用的半成品答案，别死循环。  
**生成与引用约束：**检索之后还有一步生成。一般要求答案带引用（doc_id / chunk_id），关键结论能在召回片段里找到依据；找不到就拒答或标不确定，别靠提示词硬防幻觉。简单问直接生成；复杂问在补搜结束后再生成，并做一次引用检查。  
## 3.5 接入层
一般有：问答页（带引用高亮）、知识浏览、编辑审核后台、HTTP 接口给业务系统、权限和审计日志。最好能看检索链路：改写前后 query、走了哪路、最终用了哪些片段——不然优化只能瞎猜。  
# 4. 知识的分层与运用
同一批知识，按**干净程度**和**用途**可以分成几层来管：有的适合直接回答，有的只适合兜底检索，有的只做溯源。这里的分层不是一条从上到下的流水线，需要看清两种关系：  
**加工沉淀（从下往上）：**L1 原始文档 → 自动切分成 L2 向量切片 → 再提炼成 L3 标准 QA/SOP、L4 知识图谱。L5 制度红线是单独维护的，不是从 L1 加工出来的。  
**问答使用（各层并存，按场景选用）：**L5 作为生成约束始终带上——通常以 system prompt 约束段落的形式拼接到 prompt 头部，按业务域拆分为多个规则块，生成时按问题领域动态选取；标准问优先查 L3，关联推理查 L4，口语咨询用 L2 兜底；L1 不参与回答，只用来溯源。不是每次问答都必须 L5→L4→L3→L2 一层层过。

# 5. 知识更新与生命周期
系统建好以后，真正难的是知识别「过期还在答」。更新不是单独再做一套系统，而是沿着第 3 章的加工 / 存储链路，和第 4 章的分层，把变更持续灌进去。一般按「触发 → 策略 → 按层执行 → 版本过滤」来做。  
**常见触发**  
- 源文档新增、修订、废止（L1 变更）
- 权限变更（可见范围变了，旧切片不能继续被检索到）
- 词表 / 标准 QA / SOP 人工修订（L3）
- 实体关系校准（L4）
- 制度红线、统一口径调整（L5）
- 换 Embedding 模型（向量空间变了，需重建）

**一般流程建议**  
1. 变更入库（L1 或人工编辑稿）并打上版本、生效时间、废止时间、权限标签
2. 判断走增量还是全量
3. 加工：解析 / 切片 / 向量化（L2）；需要时同步更新词表、QA、图谱候选
4. 索引切换：写入目标 collection；增量场景覆盖同 doc_id；全量场景灰度和切流
5. 失效处理：废止内容从检索过滤条件排除；热缓存主动失效
6. 抽检：用评测集里相关题目回归，确认没有「旧答案还在」
**版本与过滤：**召回结果要能带回 doc_id、chunk_id、版本、权限、时间；检索时用生效 / 废止字段和权限做过滤。换 Embedding 需重建索引并带模型版本号（见 3.2）。  
**更新频率（可参考）：**制度与红线（L5）、高频 QA（L3）变更后尽快发布；业务文档（L1/L2）按源系统能力做近实时或小时级增量；图谱（L4）适合定期批次校准。没有统一标准，按变更对业务的影响选频率，而不是所有层都实时。  
# 6. Graph 与 Agent 的接入方式
一句话：图谱管「东西怎么连着」，Agent 管「这一次怎么找」。简单问别走复杂路径。  
**流程要点：**意图分级决定走哪条路（上图）；Agent 补搜要设轮次和 Token 上限，超时降级；没有引用支撑的关键结论标不确定或拒答。路由细节见 3.4，这里只强调「简单问别上复杂路径」。

**评测集：**建议用 JSON 存，方便自动化跑分。常见字段：question（问题）、category（编号查询 / 语义咨询 / 关联推理）、difficulty（easy / medium / hard）、expected_answer（标准答案）、source_doc_ids（引用文档 ID）。示例：  
```
{
  "id": "001",
  "question": "SOP-2024-019 第 3.2 条怎么执行？",
  "expected_answer": "按第 3.2 条，需先……",
  "source_doc_ids": ["SOP-2024-019.pdf"],
  "category": "编号查询",
  "difficulty": "easy"
}
```
跑分时对照 expected_answer 判对错，检查引用是否命中 source_doc_ids，并按 category 分类统计，方便定位是哪类问题在拖后腿。  
# 9. 常见问题与规避
建设阶段常踩的坑如下。若已经上线出了问题，定位方法见第 10 章，这里不展开排查步骤。  
**固定长度一切。**条款被切碎。按结构切，条款号跟正文绑一起。  
**只用向量。**型号、错误码搜不准。上混合检索，专名进同义词表。  
**图谱很脏还硬推。**越推越错。只放校准过的核心实体；图路径要用原文再核一遍。  
**每问都 Agent。**又贵又慢。简单问短路，限制轮数，盯 Token。  
**知识不更新。**过期制度还在答。源变更要增量；生效/废止字段参与过滤。  
**靠提示词防幻觉。**不够。强制引用；没证据就拒答或标不确定。  
**检索不做权限。**答案对也可能泄密。身份和文档权限绑在过滤条件上。  
**切片粒度没调好。**切太碎丢上下文，切太大又混入无关内容、稀释语义。按文档结构定粒度，别用一个固定值套所有类型。  
**多路检索不重排。**向量、关键词各搜一批就直接喂给模型，排在前面的不一定最相关。多路结果要先融合再用 Rerank 精排。  
**Top-K 一味调大。**以为召回越多越保险，其实塞进太多低相关片段反而抬高幻觉、拉长延迟。宁可少而准。  
**没有评测集，全靠拍脑袋。**改了参数说不清是变好还是变差。先攒一批带标准答案的题，每次改动都跑一遍对比。  
# 10. 问题定位与优化策略
排查时先分清是**召回问题**还是**生成问题**：把检索到的片段直接打出来看一眼——如果关键内容压根没被检索到，是召回侧的问题，优先调切片和检索；如果内容检索到了但答得不对，是生成侧的问题，优先调 Prompt 和引用约束。下面按现象归类，对应到具体的层和一般优化方式。

<tr>

</tr>

</tr>
<tr>
