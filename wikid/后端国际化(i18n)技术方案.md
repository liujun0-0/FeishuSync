# 四、静态文案与错误码国际化（核心）
## 4.1 MessageSource 设计
```
@Configuration
public class I18nAutoConfiguration {
    @Bean
    public MessageSource messageSource() {
        ReloadableResourceBundleMessageSource ms = new ReloadableResourceBundleMessageSource();
        ms.setBasenames("classpath:i18n/error-codes", "classpath:i18n/enum-aliases");
        ms.setDefaultEncoding("UTF-8");
        ms.setCacheMillis(3_600_000);
        ms.setFallbackToSystemLocale(false);   // 关键：不回退 JVM locale
        ms.setUseCodeAsDefaultMessage(true);    // 缺失时展示 key，不抛异常
        return ms;
    }
}
```
**为什么用 MessageSource 而非硬编码 Map**：MessageSource 是 Spring 标准组件，内置 Locale 回退链（en → zh）、参数化（{0}）、热加载，性能等同 Map 查找（ConcurrentHashMap O(1)），且零维护成本。  
## 4.2 错误码枚举改造（每枚举 +3 行）（项目+枚举名称）
```
// ErrorStatusEnum.java
public enum ErrorStatusEnum implements I18nEnum {   // + implements
    USER_NOT_FOUND(404, "用户不存在"),
    BOT_NOT_FOUND(11002, "bot不存在");

    @Override                                        // + 方法
    public String getI18nKey() {
        return "error." + name().toLowerCase().replace('_', '.');
        // USER_NOT_FOUND → error.user.not.found
    }
}
```
对应 properties：  
```
# i18n/error-codes.properties（默认中文）
error.user.not.found = 用户不存在
# i18n/error-codes_en.properties（英文）
error.user.not.found = User not found
```
**现有 throw new BizException(code, desc) 一行不动** —— Advice 靠 body.getCode() 反查枚举。  
**⚠️ code 唯一性前置检查（必须）**：实测两枚举存在**同枚举内重复 code**——ErrorStatusEnum 的 11006/31006/60004 各出现 2 次；channel-receive ErrorCodeEnum 的 400001 出现 **5 次**（BIND_FAIL/BATCH_SIZE_EXCEED/DATA_EMPTY/FIELD_REQUIRED/FIELD_INVALID，message 各异）。ErrorRegistry 若用 Map&lt;Integer, I18nEnum&gt; 会被后注册覆盖，其余同码枚举将翻译成**错误文案**。处理：ErrorRegistry 支持同 code 多 key（按 key 或按 message 兜底），重复 code 的枚举在 throw 点用 I18nBizException 动态文案按场景兜底（见 §16.5），上线前先跑一次重复 code 校验。  
## 4.3 ResponseBodyAdvice 拦截翻译（必须自写）
```
@ControllerAdvice
public class I18nResponseBodyAdvice implements ResponseBodyAdvice<RestResponseVO> {
    @Autowired private I18nHelper i18nHelper;

    @Override public boolean supports(MethodParameter rt, Class<?> c) {
        return RestResponseVO.class.isAssignableFrom(rt.getParameterType());
    }
    @Override
    public RestResponseVO beforeBodyWrite(RestResponseVO body, ...) {
        try {
            if (body == null || body.isSuccess() || body.getMessage() == null) return body;
            I18nEnum e = ErrorRegistry.lookup(body.getCode());   // 主路径：code 反查
            if (e != null) { body.setMessage(i18nHelper.getMessage(e)); return body; }
            String msg = body.getMessage();
            if (msg.startsWith("error.")) body.setMessage(i18nHelper.safeGetMessage(msg)); // 可选增强
            return body;
        } catch (Exception ex) {            // 翻译失败绝不阻断业务
            log.warn("i18n fail, code={}", body.getCode(), ex);
            return body;
        }
    }
}
```
**注意**：Spring 不会"自动"翻译 —— MessageSource 只是 key 查询工具，不挂钩序列化。本拦截器的 getMessage() + setMessage() 才是真正替换动作。  
## 4.4 参数化消息（I18nBizException，实测 ~11 处）
**为什么需要 I18nBizException**  
BizException（外部 JAR）构造后 message 不可改。参数化消息（如 "剩余库存 {0} 件"）的**参数必须在 throw 那一刻替换进文案**——等响应走到 §4.3 的 ResponseBodyAdvice 时，message 已是替换后的成品（"剩余 5 件"），模板已丢失，无法再按 code 翻译。  
因此分两类处理：  
- **无参数 throw**：不改，Advice 靠 body.getCode() 反查枚举翻译（§4.2 / §4.3 主路径）
- **有参数 throw**（实测 ~11 处）：改用 `I18nBizException(enum, args)`，内部用 MessageSource 取该枚举模板 + `{0}` 填参，再 super(code, 成品)
```
// 旧：参数在 throw 前已替换，Advice 拿到成品，模板丢失、i18n 失效
throw new BizException(ErrorStatusEnum.X.getCode(),
        String.format(ErrorStatusEnum.X.getDesc(), 5));
// 新：I18nBizException 内部按 key 取模板 + {0} 填参，可翻译
throw new I18nBizException(ErrorStatusEnum.X, 5);
```
**参数化盘点（实测）**

### 4.5.2 i18n 层兜底（不纠正源码，零破坏）
方案靠 body.getCode() 反查枚举翻译，与 message 文本无关。  
- A 类（code+message 同源枚举）：完美翻译
- B 类（code 同源、message 硬编码）：仍翻译（靠 code 查）
- C 类（code 不同源）：取决于该 code 是否在 ErrorRegistry 登记
- D 类（仅 message 无 code）：无法翻译，原文透传
因此 i18n 上线**零破坏性**：不一致处只是"本次未翻译"，不会翻错。

### 4.5.4 推荐：混合策略
5. 本期：i18n 层兜底（ErrorRegistry 全量登记 + 未命中原文透传），零破坏上线
6. 短期：高频/对外暴露的几十处 throw 迁移到 I18nBizException，从源头消灭不一致

## 6.3 固定值中文字段方案（ValueI18nRegistry + 后端翻译，本期新增）
后端 `setX("中文")` 硬编码的固定值字段被前端直接展示（实测 jservice-api 62 处）。此类字段**不走前端 map**，由后端翻译。  
**① 建映射表 value→i18n key**（从现有 62 处 setX 去重扫描生成，天然支持多固定值字段，无需逐字段写 if/else）：  
```
ValueI18nRegistry
    .register("是",   "enum.yes")
    .register("否",   "enum.no")
    .register("手动", "conversation.closeType.manual")
    .register("拉黑", "conversation.closeType.block")
    .register("自动", "conversation.closeType.auto")
    .register("已连接","channel.status.connected")
    .register("未分组","dialogue.group.unclassified");
```
**② 字段白名单（必须，防止误伤用户数据）**：只对声明过的字段转换。若对所有 String 字段全局查表，会误伤用户录入的恰好等于映射值的中文。用 VO 字段注解最稳妥：  
```
@I18nValue（aa.bbb.,组概念）   // 序列化时：值 → key → MessageSource(locale) 直接输出目标语言
private String closeType;
```
**③ 出口 = 后端翻译**：序列化层对 `@I18nValue` 字段做 `ValueI18nRegistry.lookup(值) -> key -> MessageSource.get(key, locale)`，输出目标语言文案，前端原样展示（前端零翻译）。  
**④ 兜底**：查不到 key 的值 → 透传原值（不翻译不报错）；动态拼接 `"由" + name + "在后台添加"` 属 §8 动态内容，按参数化另处理。  
**⑤ 工作量**：扫描 62 处 + 建映射表 + 序列化拦截 ≈ **+0.5d**（业务枚举 NAME 输出另计）。  
# 七、Locale 解析与上下文传递
## 7.1 LocaleResolver（自写 Filter）
```
public class LocaleContextFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain) {
        try {
            I18nContextHolder.setLocale(resolve(req));  // Header → 参数 → 默认
            MDC.put("locale", I18nContextHolder.getLocale().toLanguageTag());
            chain.doFilter(req, res);
        } finally {
            I18nContextHolder.remove();   // 防内存泄漏
            MDC.remove("locale");
        }
    }
}
```
**高并发无锁**：Locale 解析为纯 CPU 计算；ThreadLocal.set() 写当前线程 map，无竞争；业务代码全程 I18nContextHolder.get() 读取，开销 ≈ 5-20ns，远低于 5ms。

## 16.3 jservice-api 缺少全局异常处理

        return RestResponseVO.fail(e);
    }
    @ExceptionHandler(Exception.class)
    public RestResponseVO<Void> handleOther(Exception e) {
        log.error("unhandled exception", e);
        return RestResponseVO.fail(new BizException(ErrorStatusEnum.UNKNOWN_ERROR.getCode(), e.getMessage()));
    }
}

## 16.4 I18nEnum 与 BizErrorCode 的关系
项目已有 `BizErrorCode` 接口（meetbot-commons），channel-receive/core-service/data-analysis 的 ErrorCodeEnum 均实现了它。新引入的 `I18nEnum` 与之重合。  
**方案**：`I18nEnum` 不应替代 BizErrorCode，而应作为 **补充接口**：  
```
public interface I18nEnum {
    Integer getCode();        // 与 BizErrorCode.getCode() 同义
    String getI18nKey();      // 新增：返回 message source key
}

// ErrorStatusEnum（裸枚举）：implements I18nEnum
// ErrorCodeEnum（已实现 BizErrorCode）：同时 implements I18nEnum
```
`ErrorRegistry` 按 code 注册任意实现 `I18nEnum` 的枚举，与 BizErrorCode 无关。  
## 16.5 ErrorRegistry 跨服务代码冲突风险
两处均定义了 `OPENAPI_KEY_INVALID(70001)`：  
- jservice-api ErrorStatusEnum.OPENAPI_KEY_INVALID(70001)
- channel-receive ErrorCodeEnum.OPENAPI_KEY_INVALID(70001)
若两服务共用同一个 ErrorRegistry，后注册的会覆盖前者。另注意**共用同一套 properties 时重复 code 也会撞单**——实测 jservice ErrorStatusEnum 中 11006×2、31006×2、60004×2；channel-receive ErrorCodeEnum 中 400001×5（ORDER_USER_SYNC_BIND_FAIL / BATCH_SIZE_EXCEED / DATA_EMPTY / FIELD_REQUIRED / FIELD_INVALID）。同一 key 只能存一个文案，翻译时同 code 命中同一文案、无法按场景区分。对策：重复 code 枚举无法靠 code 反查区分场景，throw 点直接用 I18nBizException 动态文案按场景翻译；上线前跑脚本校验重复 code，不得静默覆盖。补 code（§16.10）时应为重复枚举分配唯一 i18n key，避免 key 撞单。  
**方案**：ErrorRegistry **按服务隔离**。每个外部服务创建自己的 ErrorRegistry Bean，只注册本服务的枚举。  
```
// jservice-api
@Bean
public ErrorRegistry jserviceErrorRegistry() {
    return ErrorRegistry.of(ErrorStatusEnum.values());  // 只含 jservice 枚举
}
// channel-receive
@Bean
public ErrorRegistry channelErrorRegistry() {
    return ErrorRegistry.of(ErrorCodeEnum.values());    // 只含 channel-receive 枚举
}
```
## 16.6 ResponseBodyAdvice 执行顺序
jservice-api 和 channel-receive 已有 `CustomResponseBodyStorage implements ResponseBodyAdvice<Object>`（用于响应日志）。  
新加的 I18nResponseBodyAdvice 使用 `ResponseBodyAdvice<RestResponseVO>`，兼容，但需指定 `@Order` 控制顺序：  
- CustomResponseBodyStorage（日志）应 **先** 执行（记录原始 body）
- I18nResponseBodyAdvice（翻译）应 **后** 执行（修改 message）
两者均无 @Order 时 Spring 按类名/bean 名排序，不确定。建议显式：  
```
@ControllerAdvice
@Order(1)
public class I18nResponseBodyAdvice implements ResponseBodyAdvice<RestResponseVO> { ... }
```

## 16.10 纯硬编码字符串（D 类 "仅 message 无 code"）的翻译方案
**规模量化**

<td>channel-receive  </td>
<td>特征  </td>

</tr>

**方案（已确认）：补全 code，走主路径 code 反查翻译**  
纯硬编码无 code 的 BizException 是 Advice 的死角（code 无法查找 ErrorRegistry）。**决策：不再做文本匹配兜底，而是给这些 throw 点补全 code**，让主路径 code 反查即可翻译，语义更精准、支持参数化。具体改多少处**暂不细究**（以实际改造时扫描为准，预计 jservice ~90 / channel-receive ~15）。  
补法（两类）：  
11. **优先复用现存枚举 code**：语义可匹配的 ErrorStatusEnum / ErrorCodeEnum 条目直接复用，throw 点改为 `new BizException(Enum.X.getCode(), "中文")`
12. **语义无匹配时新增枚举条目**：为每类中文文案在枚举中新增条目（如 PARAM_INVALID / DATA_NOT_EXIST 等），再按 `new BizException(Enum.X.getCode(), "中文")` 或 `new I18nBizException(Enum.X)` 抛出
对应工作量（暂估）：  
<table>
<tr>
<td>步骤  </td>
<td>工时  </td>
</tr>
<tr>
<td>扫描全量纯硬编码字符串，归并到现存/新增 code  </td>
<td>0.3d  </td>
</tr>
<tr>
<td>新增通用枚举条目 + throw 点补 code  </td>
<td>0.4d  </td>
</tr>
<tr>
<td>**小计**  </td>
<td>**+0.7d**  </td>
</tr>

加上此补充后，总工时：**~3.5d + 0.7d = ~4.2d**，D 类从 "原文透传" 提升为 "按 code 可翻译"（动态外部消息仍透传）。  
**不推荐的做法**：  
- ❌ 正则/模糊匹配中文 → 易误翻、性能差
- ❌ 为每条硬编码字符串新增 ErrorStatusEnum 条目 → 枚举膨胀到 200+ 条，难以维护
- ❌ 在 Source 层全部改 throw new I18nBizException(Enum) → 106 处源代码改动，回归风险高
