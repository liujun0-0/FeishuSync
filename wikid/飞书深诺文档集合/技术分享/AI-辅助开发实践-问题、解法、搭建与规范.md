# AI 辅助开发实践：问题、解法、搭建与规范
---
随着 Cursor、GitHub Copilot、Claude Code 等 AI 编程工具进入日常交付，团队拿到的往往不是「写得更快」这么简单，而是一套新的协作方式：提示词成为输入、生成代码成为草稿、人工审查成为质量关口。本文从一线落地经验出发，梳理常见问题与解法，给出可复制的搭建流程，并沉淀一套面向工程的规范开发约定，方便团队统一认知、降低试错成本。  
# 一、背景与目标
AI 编程工具的价值，不在于「替人写完所有代码」，而在于缩短从意图到可验证草稿的路径。对业务团队而言，真正的目标通常有三项：提升常规需求的交付效率；降低重复样板代码与文档整理成本；在可控风险下把个人经验沉淀成可复用的提示、规则与检查清单。  
本文默认读者已有基础工程经验，关心的是「怎么用得稳」，而不是工具功能罗列。文中以 Cursor 类 Agent IDE、补全型助手（如 Copilot）以及终端 Agent 为主要参照，原则可迁移到同类产品。  
# 二、常见问题与解决思路
AI 辅助开发里最常见的失败模式，不是「模型不够聪明」，而是「人机协作没有工程约束」。下面按问题归因与应对措施展开；叙述部分成段说明，具体动作用列表列出，便于对照落地。  
## 2.1 生成内容看似正确，实际不可运行
典型表现是：编译能过、接口名也对上了，但业务规则写错、边界条件遗漏，或调用了项目里并不存在的工具函数。根因往往是模型在「看起来像」的分布上生成，而不是在「当前仓库事实」上推理；再叠加过时 SDK 记忆、错误假设的框架版本，就会出现「能看不能跑」。  
**应对思路。**把「生成」和「验证」拆成两步：生成阶段允许探索，验证阶段必须用本地命令与测试说话。具体做法如下。  
- 提示里写清技术栈版本、目录约定、禁止事项，并 @ 相关文件而不是只描述需求。
- 要求 Agent 先读再改：先定位现有实现，再给出最小改动方案，避免凭空造模块。
- 生成后强制执行编译 / 单测 / lint；失败日志原样回喂，让模型修到绿为止。
- 对关键路径人工走一遍主流程，而不是只看 diff 是否「看起来合理」。
## 2.2 上下文丢失与跨文件改动失控
长会话后模型容易遗忘早期约束，或在一次请求里同时改 UI、接口、数据库脚本，导致 diff 过大、回滚困难。跨文件时若缺少「改动地图」，还会出现一边修一边引入新不一致。  
**应对思路。**用会话边界与变更边界同时约束上下文。  
- 一个会话只服务一个目标；目标完成后开新会话，用短总结把结论带过去。
- 大需求先拆成可独立验证的小任务：接口契约 → 实现 → 测试 → 文档。
- 要求产出「将改哪些文件、为什么」的清单，确认后再动手；禁止无说明的全仓扫描式重写。
- 项目内维护 Rules：目录职责、命名、错误处理、日志规范，减少每轮重复口述。
## 2.3 过度设计与「AI 味」代码
模型倾向给出「完整、通用、可扩展」的方案，于是出现多余抽象层、过早引入状态管理、无关的配置开关，以及千篇一律的注释与异常包装。代码能跑，但维护成本上升，也不符合仓库现有风格。  
**应对思路。**把「与现有代码一致」写进硬约束，并把评审标准前移到提示阶段。  
- 明确要求：最小改动、不新增依赖、不重构无关模块、不写未请求的功能。
- 提供 1～2 个本仓库的参考实现文件，让模型模仿局部风格，而不是套通用模板。
- 对生成物做「删减法」审查：删掉不改变行为的样板后，若逻辑仍清晰，则原方案过度。
- 团队约定：超过约定行数或触及核心模块的 AI 生成 diff，必须拆 PR 或人工重写关键段。
## 2.4 安全与敏感信息泄露
风险包括：把密钥、Token、客户数据贴进提示；Agent 为「跑通」而关闭校验或放宽鉴权；生成的示例代码把密钥写进仓库；通过 MCP / Shell 执行了超出预期的命令。这类问题一旦发生，补救成本远高于开发收益。  
**应对思路。**安全默认关闭「高权限」，开放权限必须可审计。  
- 禁止在对话中粘贴生产密钥与真实客户数据；用脱敏样例或本地 mock。
- .env、凭证文件加入 ignore，并在 Rules 中写明「不得读取 / 提交敏感文件」。
- 对 Shell、网络、生产环境操作使用人工确认；破坏性命令默认拒绝。
- 合入前扫描密钥泄露；依赖与权限变更单独评审。
一条底线：AI 可以建议权限模型，但不能在无人确认时扩大攻击面。  
## 2.5 审查负担上升、责任边界模糊
生成变快之后，审查量往往同步上升。若团队默认「AI 写的差不多就能合」，缺陷会从编写阶段转移到线上。另一个问题是责任不清：出了线上事故，很难说清是提示写错、模型幻觉，还是审查人未尽责。  
**应对思路。**明确「谁提交，谁负责」；AI 输出视为草稿，合入责任仍在作者。  
- PR 描述需注明是否主要使用 AI 辅助，以及自行验证过哪些命令与场景。
- 审查清单固定化：正确性、边界、安全、性能、可回滚性；不因「AI 生成」而降低标准。
- 对高风险模块（支付、权限、数据迁移）提高人工占比，必要时禁止纯 Agent 直出。
- 用 CI 门禁扛住格式、测试、静态检查，把人的精力留给业务语义与架构。
# 三、搭建流程：从个人试用到团队可用
个人装个插件就能试用；团队要用起来，需要把「账号、权限、项目配置、质量门禁、度量」串成一条可复制路径。下面按阶段说明，避免一上来全员开通却无规范。  
## 3.1 选型与准入
选型不要只看演示效果，要按团队场景打分。关注点通常包括：是否支持仓库级规则与 Agent 多文件编辑、是否能对接内网模型或合规要求、是否支持 MCP / 终端命令、费用与席位管理是否清晰、数据是否出域。  
建议做一次为期一到两周的小范围 POC：选 2～3 个真实需求（一个 CRUD、一个缺陷修复、一个跨模块改动），记录完成时间、返工次数、安全事件与主观满意度。通过后再谈采购与推广，避免「工具很炫、落地很痛」。  
## 3.2 本地环境与账号体系
本地侧保证 Node / 语言运行时、包管理器、Docker、测试命令与团队文档一致，否则 Agent「按文档说的跑」会反复失败。账号侧统一企业席位或团队空间，避免个人免费账号混用导致权限与审计不可控。  
建议输出一份「最小可用清单」：IDE / CLI 版本、必装扩展、登录方式、模型默认档位、代理与镜像配置。新人按清单装完，应能在 30 分钟内完成「打开仓库 → 跑通测试 → 完成一次受控 Agent 改动」。  
## 3.3 项目级配置（Rules / Skills / MCP）
项目级配置是团队 AI 能力的「操作系统」。常见三类资产需要入库管理，而不是散落在个人本地。  
**Rules（规则）。**描述技术栈、目录职责、编码风格、禁止事项、提交与测试约定。规则要短而硬：能执行、能违反可感知，避免写成空洞愿景。  
**Skills（技能 / 流程）。**把高频流程写成可调用步骤，例如「按 TDD 修 bug」「发版检查」「对接飞书文档」。技能比口头提示更稳定，也便于版本演进。  
**MCP / 外部工具。**按需接入文档、Issue、监控、浏览器等能力；默认最小权限，生产写操作必须人工确认。每个 MCP 服务写明用途、权限范围与负责人。  
这些文件应随仓库评审：改 Rules 等同改工程规范，走 PR，而不是个人私改。  
## 3.4 与现有工程体系对接
AI 工具不应绕过现有工程体系，而应挂在体系上。对接点通常有四处：分支与 PR 模板提示「如何验证」；pre-commit / CI 继续执行格式与测试；Code Review 保留人工语义审查；发布与回滚流程不变。  
若团队已有脚手架、代码生成器或内部 SDK，应在 Rules 中写明「优先调用内部能力，禁止重复造轮子」。这样 Agent 会更像「懂仓库的同事」，而不是「互联网通用程序员」。  
## 3.5 试点、度量与推广
推广顺序建议：个人自愿试用 → 小组试点 → 关键路径规范固化 → 全员开通。试点期只选愿意反馈的同学，并固定复盘节奏。  
度量不必一开始就追求完美 BI，先盯几个可采集指标：同类需求周期是否缩短、返工 / reopen 是否下降、安全扫描告警是否增加、PR 平均审查时长是否失控。若效率升但缺陷与审查时长明显恶化，说明规范与门禁没跟上，应先补约束再扩面。  
# 四、规范开发：把 AI 装进工程约束
规范的核心不是限制使用 AI，而是把 AI 产出纳入与手写代码相同的质量体系。下面四条约定可直接写进团队 Wiki 或仓库 CONTRIBUTING。  
## 4.1 任务拆分与提示规范
好的提示不是「帮我实现登录」，而是把目标、约束、验收写清楚。推荐结构：背景与目标；相关文件或模块；必须遵守的约束；明确不做的事；验收标准（命令或场景）。  
任务拆分上，优先「垂直切片」：每次交付一条可验证路径，而不是横向铺开所有层。对 Agent 而言，小而完整的任务比大而模糊的史诗更不容易跑偏。  
提示示例可以固化成模板，放在仓库 `docs/prompts/` 或 Skills 中，减少每人一套方言。  
## 4.2 代码生成与变更边界
变更边界建议写成硬规则：单次 PR 只解决一个问题；无关格式化与大规模重排禁止夹带；新增依赖需说明理由；公共 API / 数据库 schema 变更必须单独评审。对 Agent 明确「只改列出的文件，其他文件只读」往往比事后删 diff 更省时间。  
若发现模型开始「顺手重构」，应立刻打断并收紧提示，而不是等 PR 再撕扯。边界清晰，是 AI 辅助开发可规模化的前提。  
## 4.3 测试、审查与合入门禁
测试策略上，优先让 Agent 补齐或更新与改动相关的自动化测试，再改实现；至少做到「改动点有断言」。审查时重点看：是否覆盖失败路径、是否 mock 过度掩盖真实集成问题、是否有 flake。  
合入门禁建议保持与手写一致：CI 绿、必要审查通过、安全扫描通过。额外建议在 PR 模板增加两项自检：已本地执行的命令列表；已知风险与未覆盖场景。作者勾选并如实填写，比「AI 生成」标签本身更有用。  
## 4.4 文档、注释与知识沉淀
AI 很擅长产出文档草稿，但也容易生成空话。约定上：对外/对业务的文档仍由负责人审定；接口说明、变更说明、运维手册可以 AI 起草，但必须对照真实代码与命令校验。  
注释只写「为什么」与非显而易见的约束，不写复述代码的废话。有效的知识沉淀形态是：可复用的 Rules / Skills、典型事故案例、脱敏后的好坏提示对照，而不是堆积未校验的长文。  
# 五、推荐工作流（可直接套用）
下面给出一条可直接套用的日常闭环，适用于中小型需求与缺陷修复。  
1. **澄清。**用一两段话写清目标、非目标、验收标准；必要时先让 Agent 只读代码并复述理解，确认无误再改。
2. **定位。**让 Agent 搜索并列出相关文件与现有实现，人工确认切入点。
3. **方案。**要求最小改动方案与文件清单；涉及架构取舍时先讨论再编码。
4. **实现。**按清单修改；中途跑测试；失败日志回喂直至通过。
5. **自检。**作者通读 diff，删除过度抽象与无关改动，补齐测试与说明。
6. **合入。**开 PR，走 CI 与审查；合并后视情况更新 Rules / 文档中的易错点。
复杂需求在步骤 3 之后增加设计评审；生产变更在步骤 6 增加发布检查与回滚预案。整条链路的关键习惯是：**先对齐事实，再生成代码；先验证，再扩大改动面。**  
# 六、落地清单与结语
若团队希望本周就开始落地，可按下列清单推进。  
- 选定工具与试点小组，完成合规与账号开通。
- 在一个核心仓库写入首版 Rules（技术栈、目录、禁止事项、测试命令）。
- 固化 PR 自检项与「作者负责制」说明。
- 跑通 3 个真实任务并复盘：效率、质量、安全、体验。
- 把复盘结论回写 Rules / Skills，再决定是否扩面。
AI 辅助开发不是用模型替代工程师，而是用工程方法约束模型，把重复劳动交给生成，把判断与责任留在人。谁能更早把「提示、规则、验证、审查」做成团队资产，谁就能在同类工具普及后仍保持可持续的交付质量。  
文档可根据团队实际工具链替换具体产品名与命令；原则部分建议保持稳定，细则随仓库演进迭代。
